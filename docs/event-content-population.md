# Event content population contract

This document defines how crawled official-site evidence becomes the data required by the Event mocks. The executable contract is `event-content-bundle/v2` in `packages/contracts/src/resolution-agent.ts`.

## Product fields and ownership

| Mock area | Canonical source | Crawler / Resolution output | Storage |
| --- | --- | --- | --- |
| Event hero | official event metadata and media | `event`, `media`, `links`, `facts`, `ticketOffers` | `event.event`, `event.event_text`, `event.event_link`, `event.event_fact`, `event.ticket_offer` |
| Schedule | official schedule/programming pages | `sessions[]` plus derived `activities[]` | `event.session`, `event.activity` |
| Exhibitors | official exhibitor/vendor/artist-alley pages | `exhibitors[]` plus booth activities | `event.exhibitor`, `event.activity` |
| Guests | official guest/programming pages | `guests[]`, session participants/targets | `event.guest`, target JSON on session/activity |
| Updates | official news/announcement pages | `updates[]` | `event.event_update` |
| Related anime/fandoms | explicit page mentions resolved against Bangumi Archive | `relatedSubjects[]`, `subjectTargets[]`, `relations[]` | `event.related_subject`, target JSON, canonical graph |
| Anime-at-event activity page | schedule + exhibitors + explicit subject mentions | `activities[]` grouped by subject and `activityType` | `event.activity` |
| Going/interested/saved/follows | KitaCon user actions | **never generated by crawler or LLM** | `consumer.event_action`, `consumer.entity_follow` |
| Trending/recommendations/friends | KitaCon ranking and social graph | **never generated by crawler or LLM** | serving/consumer projections |

Counts shown by the UI are derived from stored rows. For example, Exhibitors category counts group `event.exhibitor.categories`; anime activity counts group `event.activity.subject_targets` and `activity_type`. The model must not emit display counts that can be calculated.

## Extraction and resolution flow

```text
official pages
  -> page classification (schedule / exhibitors / guests / news / tickets ...)
  -> HTTP probe; incomplete client-rendered pages escalate to browser + XHR capture
  -> JSON-LD + rendered semantic DOM + captured JSON extraction into content.* assertions
  -> lossless evidence preparation (dedupe, collection merge, provenance, conflicts)
  -> deterministic Event Content Bundle v2 baseline
  -> adaptive evidence compaction (15k maximum by default)
  -> Anime Knowledge Service (Bangumi linking + ambiguity resolution)
  -> schema and evidence-scope validation
  -> one review Candidate
  -> human approve or link
  -> normalized event content tables
  -> Event API / serving projector
```

The deterministic baseline keeps every prepared structured record even if the model is unavailable. A successful model response is merged over the baseline by stable external key; an omitted model record cannot silently delete crawler evidence. The evidence-preparation view and Bundle v2 are produced by `@kita/evidence-pipeline`; original RawDocuments remain immutable.

For quality A/B testing, a pending Candidate can instead export its complete crawl scope and be resolved manually with Codex. The imported JSON uses the same `event-content-bundle/v2` validation and normalized materialization mapping, but is saved as a versioned editorial draft; it never overwrites the original Agent result. See [`specs/codex-event-resolution-ab-test.md`](./specs/codex-event-resolution-ab-test.md).

Resolution is enqueued only after no `URL_FETCH` or `MEDIA_FETCH` job for the crawl remains queued, retrying, leased, or running. The resolution dedupe key includes the final raw-document count. This prevents a transient `COMPLETED` status from producing a partial aggregate while concurrently discovered pages are still being committed.

## `event-content-bundle/v2`

Top-level collections:

- `event`: identity, dates, venue, official URL and organizers.
- `links`: official, tickets, schedule, exhibitors, map, updates and policy links.
- `facts`: first-held year, sourced attendance, represented-country count, duration and other sourced facts.
- `ticketOffers`: offer name, URL, price text, sale state and validity dates.
- `exhibitors`: name, booth, categories, description, site and organization names.
- `sessions`: type, title, description, times, timezone, venue/room, organizations, tags and Bangumi subject/person targets.
- `guests`: name, role, organizations and Bangumi person/subject targets.
- `updates`: title, summary, publication time, category and source.
- `activities`: normalized booth/panel/cosplay/screening/merch/meetup/guest/concert/signing/workshop records and their subject/person targets.
- `relatedSubjects`: Bangumi canonical references for the Related Fandoms/Anime views.
- `relations`, `media`, `evidence`, `conflicts`, `warnings`, `confidence`: provenance and review controls.

Every content row carries `sourceDocumentIds` and `confidence`. Every Bangumi reference contains `rawId`, legacy `encodedId`, and collision-safe `canonicalKey`.

## Limits and expected gaps

- Structured extraction uses first-party JSON-LD, rendered semantic DOM cards, and captured JSON. AUTO requests escalate to dynamic mode when generic completeness/shell signals indicate missing client-rendered content; explicit HTTP policy does not escalate.
- Booth numbers, times, attendance, organizers and relationships are returned only when evidenced. Missing values remain empty or `null`.
- Image classification continues to use crawler signals by default. Vision LLM work is optional and is not required for Event Content Bundle v2.
- Very large events may eventually split resolution into page-domain jobs. V2 already provides stable record keys and normalized tables for that migration; the current job remains one reviewed aggregate per crawl run.

## Reprocessing existing Anime Expo data

Existing crawl runs were extracted with the older connector output and will not gain `content.*` assertions automatically. After applying migration `0007_event_content_graph.sql`, run Anime Expo again, let the Resolution Agent produce a new Candidate, then approve/link that Candidate. Approval is idempotent and populates or updates all V2 content tables.

For a completed run that needs a fresh aggregate without another crawl, restart the updated Resolution Agent and call:

```http
POST /api/crawler/runs/{crawlRunId}/resolve
```

The endpoint refuses an unfinished run, AnimeCons run, or run with active crawler work. Repeating it for the same final document snapshot returns the existing resolution job.

## API read shape

`GET /api/events/{eventId}` now returns the existing event/editorial fields plus:

```json
{
  "content": {
    "links": [],
    "facts": [],
    "ticketOffers": [],
    "exhibitors": [],
    "sessions": [],
    "guests": [],
    "updates": [],
    "activities": [],
    "relatedSubjects": []
  }
}
```

Collections are sorted for display (sessions by start time, updates newest first, featured exhibitors/subjects first). This is an editorial Console API, not the final public projection. It does not return or calculate user engagement metrics in `content`.
